# Практический гайд по API-тестированию

Этот гайд относится к учебным сценариям `API-001` и `API-002` в каталоге `api-testing/test-cases/`. Примеры фактического ответа ниже не подменяют реальные результаты: их нужно получить в Postman или при запуске автоматизированного теста.

## Что проверяет API-тест

API-тест обращается к endpoint напрямую, без необходимости нажимать элементы интерфейса. Он проверяет не только статус ответа, но и заголовки, формат тела, поля, типы и значения.

Базовый цикл:

1. Сформулировать проверяемое поведение и ожидаемый результат.
2. Отправить запрос с нужным HTTP-методом, URL, заголовками, параметрами и при необходимости телом.
3. Проверить статус и заголовки ответа.
4. Разобрать response body и проверить структуру.
5. Проверить важные значения и граничные условия.
6. Записать фактический результат и приложить доказательство.
7. Присвоить статус проверки: `Passed`, `Failed` или `Blocked`.

`200 OK` само по себе не означает, что ответ корректен. Например, сервер может вернуть статус 200, но поле `price` окажется строкой, хотя контракт требует число.

## API-001 — GET /products

**Endpoint:** `GET https://fakestoreapi.com/products`

### Postman: пошагово

1. Создать HTTP Request.
2. Выбрать метод `GET`.
3. Ввести URL выше.
4. Нажать `Send`.
5. Зафиксировать полученный HTTP-статус.
6. В `Headers` проверить `Content-Type`.
7. В `Body` выбрать просмотр JSON и убедиться, что верхнеуровневая структура — массив.
8. Проверить, что массив не пустой, если это ожидается для данного учебного каталога.
9. Проверить каждый элемент: `id`, `title`, `price`, `description`, `category`, `image`.
10. Проверить типы и базовые ограничения значений.
11. Сохранить скриншот запроса и ответа или другое воспроизводимое доказательство.

### Автоматизированный тест Playwright

Файл: `tests/api/products.spec.js`.

```javascript
const response = await request.get('https://fakestoreapi.com/products');
expect(response.status()).toBe(200);
expect(response.headers()['content-type']).toContain('application/json');
const products = await response.json();
expect(Array.isArray(products)).toBe(true);
expect(products.length).toBeGreaterThan(0);
```

Дальше тест проходит по каждому товару и проверяет наличие полей, типы значений, непустое название, неотрицательную цену и отсутствие повторяющихся идентификаторов. Такие проверки должны быть согласованы с ожидаемым контрактом API.

### Чек-лист GET-проверок

| Проверка | Ожидаемый результат | Примечание |
|---|---|---|
| Статус | `200` | Для успешного получения каталога в этом сценарии |
| Content-Type | JSON | Не полагаться только на расширение URL |
| Формат | Массив | Контракт endpoint списка |
| Пустой ответ | Не пустой массив | Для учебного каталога, если сервис должен отдавать товары |
| Обязательные поля | Все присутствуют | id, title, price, description, category, image |
| Типы | Соответствуют контракту | Например, id/price — number |
| Значения | Валидны | Название не пустое, цена конечная и неотрицательная |
| ID | Уникальные | Если уникальность является частью контракта |
| Время | В рамках лимита | Только если есть согласованный порог |

## API-002 — POST /products

**Endpoint:** `POST https://fakestoreapi.com/products`

### Пример тела запроса

```json
{
  "title": "QA Portfolio Test Product",
  "price": 42.5,
  "description": "Temporary product payload for API test practice",
  "image": "https://example.com/qa-portfolio-test-product.png",
  "category": "electronics"
}
```

### Postman: пошагово

1. Выбрать `POST` и endpoint выше.
2. В `Body` выбрать `raw`, затем тип `JSON`.
3. Вставить тело запроса.
4. Убедиться, что `Content-Type: application/json` установлен. Postman обычно делает это автоматически при выборе JSON.
5. Нажать `Send`.
6. Зафиксировать фактический статус и тело ответа.
7. Проверить, что тело ответа — JSON-объект.
8. Сопоставить `title`, `price`, `description`, `image`, `category` с отправленным payload.
9. Проверить, присутствует ли идентификатор созданного объекта и каков его тип, если это ожидается контрактом.
10. Сохранить доказательство выполнения.

### Что проверяет Playwright-тест

Файл: `tests/api/products.spec.js`.

- отправляет POST с тестовым payload;
- проверяет успешный статус из разрешённого для примера набора `200` или `201`;
- проверяет JSON Content-Type;
- сравнивает ожидаемые поля ответа с отправленными значениями;
- проверяет наличие числового `id`.

### Важное ограничение Fake Store API

Fake Store API — демонстрационный сервис. Успешный ответ на POST не доказывает, что запись постоянно сохранена на стороне сервиса. Не добавлять assertion о постоянном сохранении без отдельного надёжного подтверждения поведения API.

### Негативные сценарии для изучения

- пропустить поле `title`;
- передать строку вместо числового `price`;
- отправить некорректный JSON;
- передать неожиданный Content-Type.

Для негативных сценариев сначала изучить контракт сервиса и выяснить ожидаемое поведение. Не придумывать статус ошибки: записать фактический ответ и сравнить его с контрактом.

## Как описывать результат

| Поле отчёта | Пример содержания |
|---|---|
| Test case ID | API-001 |
| Request | GET `/products` |
| Expected | 200, JSON-массив с обязательными полями |
| Actual | Заполнить после реального выполнения: статус, Content-Type, форма JSON |
| Evidence | Скриншот Postman, экспорт ответа без секретов или автоматизированный отчёт |
| Status | Passed / Failed / Blocked |

Не заполнять `Actual` предполагаемыми значениями. Если запрос не отправлялся, указывать `Not run`. Если API недоступен и выполнить проверку невозможно — `Blocked`, не `Failed`.

## Запуск автоматизированных API-тестов

```bash
npm install
npx playwright install chromium
npm run test:api
```

Эти тесты обращаются к внешнему сервису, поэтому требуют подключения к интернету и могут зависеть от доступности стороннего API. Для воспроизводимых UI-тестов используются локальные тестовые данные.
