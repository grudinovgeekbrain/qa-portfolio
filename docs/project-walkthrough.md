# Как устроен учебный QA-проект

Документ описывает текущее состояние репозитория и помогает подготовиться к обсуждению проекта на собеседовании. Это учебная практика, а не заявление о коммерческом опыте.

## 1. Объект тестирования

`web-testing/online_market.html` — одностраничный демонстрационный интернет-магазин. HTML, CSS и JavaScript находятся в одном файле.

- HTML задаёт структуру каталога, поиск, сортировку и корзину.
- CSS отвечает за оформление карточек и элементов интерфейса.
- JavaScript загружает каталог, фильтрует и сортирует товары, управляет корзиной и обрабатывает события.

Отдельного backend и собственной базы данных у приложения нет. Каталог загружается через Fake Store API, а корзина хранится в `localStorage`.

## 2. Как работает приложение

Основные данные и состояния:

- `originalProducts` — исходный массив товаров из API;
- `products` — товары, отображаемые после поиска и сортировки;
- `cart` — товары и их количество в корзине;
- `searchQuery` — поисковая строка;
- `sortType` — выбранный порядок сортировки.

При инициализации приложение восстанавливает корзину из `localStorage`, отображает её и запрашивает каталог. После получения товаров функция обновления каталога применяет поиск и сортировку, а затем перерисовывает DOM.

## 3. Ручное тестирование

В репозитории есть smoke-чек-лист, функциональные тест-кейсы и четыре баг-репорта/наблюдения с разным статусом подтверждения.

Важно различать подтверждённый дефект и гипотезу. В документах указаны статусы проверки; не следует представлять наблюдение как воспроизведённый дефект без фактических доказательств.

## 4. UI-автоматизация Playwright

Файл: `tests/ui/store.spec.js`.

Набор содержит проверки:
- отображения каталога;
- поиска с учётом регистра и поиска без совпадений;
- сортировки по цене в обоих направлениях и сброса фильтров;
- добавления товара, увеличения количества, удаления позиции и очистки корзины;
- сохранения корзины после перезагрузки;
- отображения сообщения об ошибке при ответе каталога со статусом 503.

Для стабильности UI-тесты используют mock-ответ с тремя заранее известными товарами. Поэтому они проверяют поведение интерфейса, а не доступность настоящего Fake Store API.

## 5. API-автоматизация Playwright

Файл: `tests/api/products.spec.js`. Содержит два теста.

### GET /products
Проверяются статус 200, Content-Type, JSON-массив, наличие товаров, обязательные поля, типы данных, базовые ограничения значений и уникальность ID.

### POST /products
Отправляется тестовый JSON-payload. Проверяются успешный статус из допустимого в данном тесте набора 200/201, JSON Content-Type, соответствие возвращённых полей отправленным значениям и наличие числового ID.

API-тесты обращаются к внешнему сервису и требуют интернета. Успешный ответ Fake Store API на POST не доказывает постоянное сохранение товара в базе данных.

## 6. Конфигурация и локальный запуск

- `package.json` — зависимость Playwright и команды запуска.
- `playwright.config.js` — папка тестов, браузер Chromium, таймауты, репортёр, трассировка, скриншоты и локальный web-сервер.
- `scripts/static-server.js` — небольшой HTTP-сервер на встроенных модулях Node.js, который отдаёт файлы приложения во время UI-тестов.
- `tests/README.md` и `docs/automation-guide.md` — краткая карта тестового набора и объяснение запуска.

Установка зависимостей и браузера:

```bash
npm install
npx playwright install chromium
```

Запуск в PowerShell, где скрипт `npm.ps1` может быть заблокирован политикой исполнения:

```powershell
npm.cmd run test:ui
npm.cmd run test:api
```

В обычном CMD обычно достаточно `npm run test:ui` и `npm run test:api`.

## 7. GitHub Actions

Workflow `.github/workflows/playwright.yml` запускается при `push`, `pull_request` или вручную. Он устанавливает Node.js, зависимости и Chromium, затем запускает `npm run test:ui` и загружает HTML-отчёт.

Сейчас workflow автоматизирует UI-тесты. API-тесты можно запустить отдельно командой `npm run test:api`; они зависят от доступности стороннего API.

## 8. Ограничения и что не следует преувеличивать

- Учебное приложение не имеет backend, собственной базы данных и настоящего checkout/payment flow.
- UI-тесты используют mock каталога; это не проверка доступности реального API.
- API-тесты зависят от внешнего Fake Store API.
- Баг-репорты имеют разные статусы. Для кандидатов, требующих подтверждения, нужны воспроизведение в браузере и доказательства.
- Наличие автотеста не означает, что всё приложение протестировано исчерпывающе; текущий набор покрывает перечисленные сценарии.
